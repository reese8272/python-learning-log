## What we covered

### The problem with the while loop
The basic agent loop is a `while True` with one fork: tool call or done. It has two production-killing limitations:

1. **Unbounded state growth** — the messages list grows forever. Long agents hit context limits and get expensive.
2. **No persistence** — state lives in a Python variable in RAM. Process dies mid-task, everything is gone. No recovery, no resume, no debug trail.

The loop also has a silent bug: it only handles `tool_calls[0]`. Real LLMs return parallel tool calls — the rest are silently dropped.

### Why branching is the deeper problem
The loop can't express routing. Real agents need to go different directions based on what the LLM returns — route to finance agent, route to code agent, pause for human input, run two agents in parallel. None of that fits in an `if/else` bolted onto a `while True`.

### LangGraph — three concepts

| Concept | What it is |
|---|---|
| **State** | A typed object saved to a DB after every step — not a list in RAM |
| **Nodes** | Functions that take state, do something, return updated state |
| **Edges** | Connections between nodes — fixed or conditional |

**Conditional edge pattern:**
```python
def route(state):
    if state["next"] == "finance":
        return "finance_agent"
    elif state["next"] == "code":
        return "code_agent"
    else:
        return "end"

graph.add_conditional_edges("supervisor", route)
```
The LLM sets `state["next"]`. The edge reads it. The graph routes. Decision is in the graph structure, not buried in loop logic.

### State — what's in the messages array
```python
[
    SystemMessage("..."),      # you write this
    HumanMessage("..."),       # user input
    AIMessage(tool_calls=[]),  # LLM response
    ToolMessage("..."),        # tool result
    AIMessage("..."),          # final answer
]
```
The full history is passed back to the LLM each turn. There's no separate memory object — history IS state.
