## Live research (Rule 1)

- [FastAPI — *Concurrency and async/await*](https://fastapi.tiangolo.com/async/) — verified verbatim: *"When you declare a path operation function with normal `def` instead of `async def`, it is run in an external threadpool that is then awaited, instead of being called directly (as it would block the server)."* Same treatment for `def` **dependencies**.
- **What that page does NOT say — and this is the finding.** Confirmed live: it contains **no warning about blocking calls inside `async def`**, and **no mention of the threadpool's size**. The two facts that decide p99 are both absent from the official page. (Same gap noted 08-11.)
- [anyio — *Working with threads*](https://anyio.readthedocs.io/en/stable/threads.html) — verbatim: *"The default AnyIO worker thread limiter has a value of **40**."* Adjusted via `to_thread.current_default_thread_limiter().total_tokens = 60`.
- [Kludex — `fastapi-tips`](https://github.com/Kludex/fastapi-tips) (Starlette maintainer) — *"There are only 40 threads available in the thread pool. If you use all of them, your application will be blocked."* Also: `PYTHONASYNCIODEBUG=1` warns on tasks >100ms; `limiter.borrowed_tokens` for live thread counting. **Both held for 1.2b.**
- Chain confirmed: FastAPI → Starlette `run_in_threadpool` → `anyio.to_thread.run_sync` → capacity limiter (40).

## What was taught — chunk 1.2a: the three-way routing rule

The core reframe: everyone learns this as a **two-way** decision (`async` fast / `def` slow). It's **three-way**, and FastAPI picks by inspecting the signature.

| You write | FastAPI does | Concurrency budget |
|---|---|---|
| `async def` + only awaitables | runs **on the event loop** | unbounded |
| plain `def` | ships to the **threadpool**, awaits it | **40** |
| `async def` + a **blocking** call | runs on the loop — **and the loop stops** | **1** |

Row three is not a slower row one. It's a **worse row two**, and the only one the framework can't help with, because from the outside it looks identical to row one.

**The rule, in producible form:**
> **`await` is the loop's only escape hatch. If a line takes real time and has no `await` in front of it, the loop is stuck on that line.**

**`async def` is opting *out* of the safety net** — you're telling FastAPI "I've got this, don't wrap me," and it believes you.

**The §1.3/§4 tie-in, front-loaded deliberately:** the 40 is **one shared pool per process** — `def` handlers *and* `def` dependencies both draw from it. A sync `requests`-based JWKS fetch in the JWT dependency burns a token on every authenticated request, so **the auth layer silently sets the concurrency ceiling for the entire API.**

Three-way snippet delivered (`/a` ~100s · `/b` ~4s · `/c` ~2s): same intent, 50× spread. **The keyword didn't do it — the `await` did.**

**Taught in response to his question:** `async with` = context manager (his own `open(file) as f` analogy, confirmed); the `async` prefix means `__aenter__`/`__aexit__` are coroutines so setup/teardown can themselves await. Plus the production correction to my own snippet: per-request `AsyncClient` throws away the connection pool and re-does TLS every call — real version hoists it to app state (**forward ref to §1.7 `lifespan`**, and to where the JWKS client will live in §4).

**② the answer he owed:** all three candidates produce high latency, so latency isn't the signal. **Undersized instance → CPU pegged, not idle** (ruled out instantly). **Slow DB → slow even at concurrency 1.** **Blocked loop → a single request is *fast*; latency is purely queue depth**, scaling linearly with rate while CPU stays flat. The discriminating test is one sentence: *"send one request to an idle box."*

**③ the caveats added:** batches are **integer**, so the knob is lumpy (40→80 took 25s→15s, not 12.5s). And raising `total_tokens` isn't free — 80 OS threads on a 0.25-vCPU Fargate task is real memory and scheduler pressure, and you just doubled concurrent load on the downstream service. Valid lever, **last** lever.
