# Senior Engineering — Soft Skills & Social Craft Roadmap

**What this is:** A ground-up curriculum for the *human* layer of great engineering — the work and struggle of becoming a senior engineer in a real org: communication, judgment made visible, disagreeing well, multiplying others. Built the same way as the AI and Python tracks: each unit is learned in-catalog via `/learn` (researched live against current authoritative writing), then applied in a real interaction. This roadmap is the *what to cover*; the teaching is generated fresh each session so it never goes stale.

**Why this track exists (Reese, 2026-07-07):** Technical skill gets the interview; the soft/social layer is the multiplier and the differentiator — and at ~1yr in, aiming at $120k+ roles, it's the single highest-leverage thing to build on top of a strong technical trajectory. "Just as important as everything else." These behaviors are available *now*, not at some future title.

**How this track differs from the technical tracks:**
- **No runnable `.py` worksheet.** There's no code to green-light "communicate well." Forcing a `pytest` harness onto soft skills would be ceremony. The rigor stays (live-researched, tied to his situation, struggle-first) — but the artifact is different.
- **Build-before-bank = a real interaction, not code.** A unit banks when he *applies* it somewhere real: an interview answer, a Slack/PR message, a standup, a design doc. Five minutes of real application counts.
- **No `/sharpen` cold-defense queue.** These aren't defended in `concept_queue.md` (that's the technical `/sharpen` backlog). Soft-skills "defense" is deployment under real conditions. `/drill` can still resurface the key one-liners.

**Currency note:** Soft skills don't rot like an API — but research each unit's *framing* live anyway (the field's best articulations evolve, and named frameworks give citation weight + a resource pool). Never teach from memory; it's the discipline of the system.

**Anchor sources (the resource pool for this whole track):**
- **Will Larson** — *Staff Engineer* / [StaffEng.com](https://staffeng.com) — the scope/impact and archetype framing.
- **Tanya Reilly** — *The Staff Engineer's Path* + her talk **"Being Glue"** — ambiguity, glue work, being concrete over safe.
- **Camille Fournier** — *The Manager's Path* — the leadership/communication ladder from the IC side.
- **Gergely Orosz** — *The Pragmatic Engineer* — current industry practice on levels, visibility, influence.

**Tiers:**
- **Tier 1 — Load-bearing** → can articulate it cleanly AND has applied it in a real interaction. Mechanism + why-this-matters + failure mode.
- **Tier 2 — Situational** → aware of it, can deploy it when the moment calls, one-line why.

**Status keys:** `[ ]` not started · `[~]` taught, real-application pending/partial · `[x]` owned (date) — taught + applied in a real interaction.

**How to use:** Work top-down; the mindset unit underpins the tactics. `/learn soft` walks this file. Don't skip a `[ ]` because it "sounds obvious" — the gap is usually *behavioral* (knowing what it looks like / doing it), not conceptual.

## The Units

### Tier 1 — Load-bearing

- [~] **1. Scope of impact** — the mindset shift "my code" → "the team's outcome." Impact is measured by the delta you create in others, not your individual output. The concrete behavioral model (kill ambiguity · concrete-over-safe · multiply via review+teaching · question the requirement · glue work). Failure modes: the hoarder/hero (bottleneck) and the martyr (glue trap). *(taught 2026-07-07; build attempted — output→senior-frame rewrite of the Cognizant Playwright work, graded B: real "A over B" tradeoff and team-outcome still to fill in. Refine → then `[x]`.)*
- [ ] **2. Communicating to reduce ambiguity** — writing/speaking so shared context *increases*. BLUF ("bottom line up front"), audience-tuning, the design-doc muscle. Reilly's "wrong gets corrected, vague sticks around" in practice.
- [ ] **3. Disagreeing well** — strong opinions loosely held, disagree-and-commit, how to push back on someone senior without torching trust. Separating the idea from the ego.
- [ ] **4. Code review as a relationship** — reviewing to *teach* (compounding) not gatekeep (linear); giving feedback that lands; receiving review without defensiveness.

### Tier 2 — Situational

- [ ] **5. Making your work legible** — being valued without self-promotion feeling gross. The honest version of visibility/managing-up: brag docs, status that reads as impact, letting the right people see the reasoning.
- [ ] **6. Glue work & mentorship** — the invisible connective work that *makes* seniors, done without becoming a martyr. Unstick-enough-then-hand-back; keeping your own signal visible while multiplying others.

## Honest Takeaways

*(What actually landed vs. didn't — update as units complete.)*

- **Unit 1 (2026-07-07):** The *thesis* (force-multiplier for others) landed cold on the first probe — he already had it. The real gap was the **behavioral model** ("I don't know what I'm looking for in a senior"). Filling that — the concrete list of what a senior *does* — was the unlock. The build showed the recurring edge: he reaches for the *obvious* tradeoff (Playwright vs manual) instead of the *real* one (Playwright vs Cypress) and drops the team-outcome. That's the muscle to keep training: name the hard decision and the effect on others.
