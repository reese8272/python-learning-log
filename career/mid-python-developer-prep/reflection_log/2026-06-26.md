## Live research (cited)
- **Python Data Model** (docs.python.org/3/reference/datamodel.html) — confirmed verbatim rule: *"A class that overrides `__eq__()` and does not define `__hash__()` will have its `__hash__()` implicitly set to `None`."* Plus the mutable-key rationale (don't hash mutable objects).
- **CPython small-int cache** — confirmed range **−5 to 256** (Real Python / multiple current sources). Stable through 3.13.

## Taught (current pattern, Tier 1 bar)
1. **`is` vs `==`** — `is` = identity, `==` = value. Small-int cache (−5..256) makes `4 is 4` True but `1000 is 1000` False → *never use `is` on values; reserve it for `None`/`True`/`False`.*
2. **Mutable default** — default evaluated **once at def-time**, so `bucket=[]` is one shared object that leaks. Fix = `None` sentinel + `if bucket is None`.
3. **`__eq__`/`__hash__` contract** — defining `__eq__` sets `__hash__` to `None` → object unhashable (TypeError as set member / dict key). Invariant: `a == b` ⇒ `hash(a) == hash(b)`. Fix: define `__hash__` over the same fields. THIS-over-THAT: immutable value object → define `__hash__`; mutable entity → leave it unhashable.
4. **First-class functions** — a bare function name *is* a passable value (`x = shout`, no parens); `apply(fn, value)` pattern. This is what makes decorators, `sorted(key=...)`, and (forward ref to §3) `Depends()` work. Had to re-teach this from zero, stripped of FastAPI; he asked good questions.
